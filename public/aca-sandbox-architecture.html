ACA Sandbox Architecture: one controller for lifecycle and runtime

Local and hosted Workbench use one Sandbox Controller for lifecycle and runtime operations. The controller owns durable lifecycle coordination and relays volatile authenticated streams to sandbox bridges, xDS-style. Agent state stays in sandboxes; secret delivery uses ACA-managed injection instead of sandbox files.

Dev user and Prod user are browser entry points on the same laptop. Local development defaults to PGlite; the dashed database route is opt-in. Workbench PostgreSQL stores domain data; Controller PostgreSQL stores lifecycle coordination only. No Agent runs locally, and neither database stores Agent transcripts or sandbox files. Both Workbench servers are replaceable and contact only Sandbox Controller for sandbox lifecycle and runtime operations. It calls Microsoft ACA control/data-plane APIs for lifecycle and maintains authenticated runtime streams to sandbox bridges, xDS-style. Runtime frames are relayed transiently—not stored in Controller PostgreSQL, logs or queues. This is one service, not a controller plus a separate gateway.

1. Runtime streams through the same controller

Workbench sends both lifecycle and runtime operations to Sandbox Controller. The controller uses ACA APIs for lifecycle and relays runtime frames over authenticated sandbox-bridge streams, xDS-style, rather than repeated ACA exec calls.

The sandbox bridge is the runtime endpoint behind the controller, not an endpoint given to Workbench. Both development and production use Workbench ↔ Sandbox Controller ↔ sandbox bridge. Only the controller selects the fenced allocation and maintains the southbound stream. Runtime traffic is transient; durable Agent state remains sandbox-owned.

2. Secret delivery through the Sandbox Controller

Stop staging credentials as files that must later be removed through the same unreliable exec path.

The credential-bootstrap work keeps the capability, nonce and locator out of command text, URLs, files and diagnostics. ACA injects them only on the exact approved outbound request to Sandbox Controller. The controller validates the request and transiently relays the authorized bootstrap response; the launcher passes credentials only to the intended child process. Bootstrap capabilities are not Workbench-to-sandbox connection grants.
